# ADR-005：伤害结算流程

> 状态：已确定
>
> 创建日期：2026-10-23
>
> 决策日期：2026-10-23
>
> 决策依据：2026-10-23 确认采用 DSH 修订版，本文作为正式 ADR 维护。
>
> 本记录描述架构决策；“已确定”不表示接口已定稿或代码已实现。实现与验证进展见第 7 节。
>
> 摘要：命中与段数归技能层；伤害按“暴击 → 格挡 → 计算 → 施加”的固定顺序结算；直接伤害与百分比伤害共用一条流水线和一个施加出口，但使用两套公式；阶段之间信息单向流动。

## 1. 背景

战棋的核心系统是技能与 Buff，而两者最终都要回答同一个问题：一次攻击或一次持续效果，扣多少血、什么时候扣、什么时候死。伤害流程如果不先定稿，技能、Buff、AI、UI 就会各自实现一套扣血逻辑，后续很难收敛。

数值模型参考宝可梦：

$$
Damage = Power \times \frac{Attack}{Defense} \times Modifier
$$

- `Power`：技能威力。
- `Attack` / `Defense`：由技能声明的攻防属性对，取当前值（含 Buff 修正，见 [ADR-003](ADR-003-Buff改变Attribute的方式.md)）。物理、魔法或自定义属性都可以接入同一公式，不把“攻击/防御”硬编码为全局属性。
- `Modifier`：暴击、格挡、属性克制（暂缓）、背刺/侧击、Buff 增伤/减伤等修正的乘积。

除直接伤害外，还有以最大生命值为基准的百分比伤害：寄生种子、沙暴、灼烧、中毒等。这类伤害不需要命中、暴击、格挡，也不接受通用 `Modifier`；但可以被“毒疗”一类效果取消并转为治疗。

作出本决策前，已有两个方向：命中归技能层；直接伤害按“暴击 → 格挡 → 计算 → 施加”的顺序结算。仍需明确两类伤害是统一还是分离、每个阶段的边界与 Hook 权限，以及后发生的阶段能否反过来影响先发生的阶段。本文确认这些规则，作为后续接口设计与实现的依据。

约束：

- 项目使用 UE + C++、Code-First（[ADR-002](ADR-002-采用Code-First开发方式.md)），MVP 优先。
- 单机回放与自动化测试要求确定性；网络同步暂不纳入。
- 本文只决定伤害流程；Buff 生命周期、命中判定的具体规则、Hook 派发机制分别由其他文档负责。

术语约定：本文把一次待结算的伤害称为一个 **Context**（伤害上下文）；流水线的一步称为**阶段**；阶段前后的 Hook 点称为**检查点**；结果为 0 的免疫/完全格挡称为**否定**（`Negated`）。

## 2. 面临的问题

本 ADR 要回答两个问题，并划清一条边界：

1. 一次伤害从“技能确认命中”到“扣血/死亡”的完整流程是什么？各阶段由谁负责、按什么顺序、读写哪些数据、允许哪些介入？
2. 直接伤害与最大生命值百分比伤害，应当统一成一套流程，还是分成两套？
3. 边界：命中、on-hit、DOT tick、死亡处理分别属于技能层、伤害层还是 Buff/战斗流程？

第 3 个问题是第 1 个问题的一部分，但它决定了接口切分，因此单独列出。

判断标准（按优先级）：

1. **语义清晰、可预测**：同一输入产生同一结果，顺序不依赖注册的偶然性。
2. **可扩展**：新增技能/Buff 尽量不改流程本身。
3. **可测试、可回放**：能对单阶段和组合写确定性测试。
4. **实现与维护成本**：MVP 阶段不引入不必要的抽象。
5. **对内容设计的限制必须显式记录**，而不是留给实现者猜。

## 3. 候选方案

两个问题分别比较；表中的“采纳/否决”记录本次正式决策。收益与风险是设计判断，尚未用实现验证。

### 3.1 问题 1：命中与伤害流程的边界

| 方案 | 核心做法 | 优点 | 代价与风险 |
| --- | --- | --- | --- |
| A1：命中并入伤害 | DamageCmd 先掷命中，再继续结算 | 调用方只需发一条指令 | 变化技能没有伤害却要命中；多段段数无法在技能层确定；on-hit 与 on-damaged 混在一起。否决。 |
| B1：命中归技能层 + 固定阶段流水线 | 技能层输出已确认的命中段；DamageCmd 只结算这些段 | 职责清晰；支持变化技能与多段；命中/受伤事件分离 | 技能层需要命中契约；跨层调试成本上升。采纳。 |
| C1：完全事件驱动 | 技能只发事件，各效果自行订阅并决定顺序 | 灵活 | 顺序不可预测；容易循环依赖；难以测试和回放。否决。 |

### 3.2 问题 2：两类伤害的关系

| 方案 | 核心做法 | 优点 | 代价与风险 |
| --- | --- | --- | --- |
| A2：完全分离 | 直接伤害与百分比伤害各自计算、各自扣血 | 各自简单，互不影响 | 扣血/溢出/死亡/受伤事件重复实现；毒疗、吸血、反伤要写两套。否决。 |
| B2：完全统一 | 百分比伤害也走 `Power × Attack / Defense × Modifier` | 只有一条公式 | 百分比伤害没有攻防与命中，语义扭曲；DOT 的可靠性被防御属性破坏。否决。 |
| C2：一条流水线、两套公式、一个施加出口 | 阶段与 Hook 名称统一；公式按伤害形式选择；所有伤害在同一施加点落地 | 事件/扣血/死亡唯一；DOT 语义独立；扩展新形式只加公式 | 需要形式适用性表；Hook 作者要感知形式。采纳。 |

## 4. 最终决定

采用方案 B1 与 C2：命中与段数归技能层，伤害按固定阶段结算；直接伤害与百分比伤害共用一条流水线、两套公式和一个施加出口。以下规则为本次确定的架构约束；明确标注为预留或待定的扩展不在本次决策范围内。

### 4.1 命中与段数归技能层

- 技能层负责：目标选择、命中判定、命中段数/段列表、消耗与冷却。命中率的具体规则（技能命中、目标闪避、地形等）属于技能/战斗流程，不在本文展开。
- 技能层输出“已确认的命中段”（`ConfirmedHits`）：每段包含目标、威力、伤害形式、标签。
- DamageCmd 不再掷命中；它只接收已确认的伤害段并结算。
- on-hit（命中时）效果在技能层触发；on-damaged（受伤时）在施加阶段触发。二者不是同一个事件。
- 多段技能可以由技能层采用不同策略，例如：
  - 一次判定决定总段数，全部命中（如种子机关枪式的 2–5 段）。
  - 逐段判定，未命中即停（如鼠数儿式连击）。
- 技能层在每段前后检查施放者与目标是否有效；施放者死亡或目标已死亡时，停止剩余段（多目标时只停止该目标）。

### 4.2 伤害流水线

所有伤害都走同一条流水线；伤害形式决定哪些阶段生效、用哪个公式。

```text
技能层：确认命中段
└─ 每段创建一个 Context
   ├─ 1 暴击判定    BeforeCrit / AfterCrit
   ├─ 2 格挡判定    BeforeBlock / AfterBlock
   ├─ 3 计算        BeforeCalc / AfterCalc
   └─ 4 施加        BeforeApply / AfterApply
                    └─ HP 归零 → OnDeath

Buff / 环境 tick：创建百分比伤害 Context
   ├─ 跳过 1、2
   ├─ 3 计算（MaxHealth × Ratio）
   └─ 4 施加（与直接伤害同一出口）
```

规则：

1. **顺序固定**：暴击 → 格挡 → 计算 → 施加，不随技能或 Buff 改变。需要“先格挡后暴击”的内容，应改写为追击包或持续效果，而不是改流程（见 6.1）。
2. **信息单向流动**：阶段只能读取已完成阶段的结果，不能回写。`AfterBlock` 可以影响第 3 步的伤害，但不能改变第 1 步的暴击结果。这是解决“格挡影响暴击”冲突的核心规则，而不是临时限制。
3. **每阶段两个检查点**：`BeforeX` 修改本阶段尚未定稿的输入，并可否定本阶段的结果（如免疫暴击、免疫格挡）；`AfterX` 读取本阶段已定稿的结果，只能影响后续阶段或后续伤害包，不可撤销。同一阶段同时出现强制与免疫时，否定优先。
4. **修正因子乘算**：按固定类别顺序相乘——暴击 → 格挡 → 属性克制（预留）→ 位置（背刺/侧击/高地）→ 独立增伤/减伤。固定顺序只影响浮点取整与明细展示，不代表因果顺序；在实数上乘法可交换。位置类修正由战斗/棋盘系统在创建 Context 时提供，伤害流程不判断站位。
5. **概率加算、倍率取属性**：暴击率与格挡率按百分点加算，再限制在 `[0,1]`；暴击倍率与格挡倍率取对应属性的当前值（同一属性的多个 Buff 已由 ADR-003 合并）。独立增伤/减伤每个来源各自成因子相乘，因此两个 10% 减伤是 `0.9 × 0.9 = 0.81`，而不是 `0.8`；这是有意的收益递减。内容文本中的“暴击率 +50%”默认按百分点解释；相对提升需显式写成倍率。
6. **取整与最低伤害**：用双精度计算，最后向下取整一次；每段独立取整，不先求和再取整。直接伤害与百分比伤害在未被否定时最低 1 点；`Power = 0`、`Attack = 0` 或 `Ratio = 0` 时结果为 0，不适用最低 1 点。攻击属性下限为 0，防御属性下限为 1，避免除零。
7. **否定用标志，不用 0 因子**：免疫、完全格挡、无效化用 `Negated` 表达，结果为 0；所有乘算因子必须大于 0。这样“最低 1 点”不会把完全格挡恢复成 1 点。被否定的包不进入扣血与受伤事件；替换效果自行触发对应事件（如治疗）。所有 0 结果都必须用 `Negated` 表达，不能只把施加量改成 0。
8. **随机数契约**：暴击/格挡使用战斗级、可播种的随机数；判定方式为一次均匀随机数与概率比较，具体算法不限但同一版本内固定。消耗顺序固定为按段序、每段先暴击后格挡。伤害预览与 AI 评估使用不掷骰的期望值函数，不得消耗战斗随机数。反应产生的新伤害包进入 FIFO 队列，在当前包完成后结算；队列中的包在结算前重新校验目标有效性，需要命中判定的反应先由技能层确认再入队；队列设深度上限，防止无限反伤。
9. **多目标与多段**：多目标按技能声明的固定顺序（选择顺序或格子顺序）逐个结算，不并行；同一目标的多段默认每段独立暴击/格挡/取整。技能若需要“全段同暴击”，在技能层掷一次并在 `BeforeCrit` 强制结果。
10. **死亡判定**：扣血时 HP 下限为 0，`Overkill` 记录超出部分；HP = 0 立即判定死亡；`AfterApply` 仍会触发（用于反伤、吸血、击杀奖励），但不能撤销死亡；`OnDeath` 在 `AfterApply` 之后触发。免死/保留 1 HP 属于 `BeforeApply` 的施加量修正。

### 4.3 两类伤害：一条流水线、两套公式、一个施加出口

采用 3.2 的方案 C2。

| 阶段 | 直接伤害（Direct） | 百分比伤害（PercentMaxHealth） | 固定伤害（Fixed，预留） |
| --- | --- | --- | --- |
| 命中 | 技能层判定 | 不适用（由来源决定是否施加） | 技能层 |
| 1 暴击 | 生效 | 跳过 | 待定 |
| 2 格挡 | 生效 | 跳过 | 待定 |
| 3 公式 | `Power × Attack / Defense × ΠModifier` | `MaxHealth × Ratio` | 常量（待定） |
| 通用 Modifier | 生效 | 不生效 | 待定 |
| 4 施加 | 生效 | 生效 | 生效 |

- “一个出口”指第 4 步只有一份实现：取消/替换、扣血、溢出记录、受伤事件、死亡处理、伤害数字都只在这里发生。
- “两套公式”指第 3 步按伤害形式选择计算方式；百分比伤害不进入暴击/格挡，也不接受通用 `Modifier`。
- 跳过不等于另一条流程：阶段定义、命名、顺序、施加出口都是同一套，只是该形式不适用某些阶段；不适用的阶段不触发对应 Hook。
- 百分比伤害的“抵消/反转”（毒疗）不是 `Modifier`，而是第 4 步的取消与替换，因此不受“百分比伤害不吃修正”的限制。
- `Fixed` 只作为扩展位占位，本文不决定它是否吃 `Modifier`、是否受暴击/格挡；引入时需补充公式与适用性。
- 本文不规定用继承、策略还是表驱动实现；只要求阶段名、顺序、权限与出口一致。

### 4.4 Context 需要携带的信息

以下字段是概念清单，不构成最终接口承诺。

| 字段 | 含义 |
| --- | --- |
| `Source` / `SourceEffect` | 负责单位 / 直接来源（技能、Buff、环境）。`Source` 可为空（环境伤害）。 |
| `Target` | 承受者。 |
| `Form` | `Direct` / `PercentMaxHealth` / `Fixed`（预留）。 |
| `Power` / `Ratio` | 直接伤害的威力 / 百分比伤害的比例。 |
| `AttackAttribute` / `DefenseAttribute` | 技能声明的攻防属性对。 |
| `Tags` | 来源标签（`Poison`、`Burn`、`LeechSeed`、`Weather`、`Counter` 等），供 Hook 过滤。 |
| `HitIndex` / `HitCount` | 段序号 / 总段数。 |
| `bCrit` / `bBlocked` / `bNegated` | 判定结果与否定标志。 |
| `bForcedCrit` / `bCannotCrit` / `bForcedBlock` / `bCannotBlock` | 阶段内的强制/免疫标志；否定优先于强制。 |
| `RawAmount` / `AppliedAmount` / `Overkill` | 计算值 / 实际扣血 / 溢出。 |
| `Breakdown` | 各阶段前后值、修正因子明细、随机数消耗记录，供日志与测试。 |

`Source` 与 `SourceEffect` 分开：寄生种子的 `Source` 是施放者、`SourceEffect` 是种子 Buff；反伤的 `Source` 是被攻击者、`Target` 是攻击者。

### 4.5 算例

`Power = 60`，`Attack = 120`，`Defense = 80`，暴击率 20%，暴击倍率 1.5，格挡率 25%，格挡倍率 0.5。

| 结果 | 计算 | 伤害 |
| --- | --- | --- |
| 未暴击、未格挡 | `60 × 120 / 80` | 90 |
| 暴击、未格挡 | `90 × 1.5` | 135 |
| 未暴击、格挡 | `90 × 0.5` | 45 |
| 暴击、格挡 | `90 × 1.5 × 0.5 = 67.5` | 67（向下取整） |
| 完全格挡 | `Negated` | 0 |
| 防御极高 | `60 × 120 / 10000 = 0.72` | 1（最低伤害） |

## 5. 决策理由

### 5.1 为什么命中归技能层

- 变化技能没有伤害，但可以有命中/抵抗（如催眠、电磁波）。如果命中在伤害里，变化技能就得走一条没有伤害的伤害流程。
- 多段技能的段数、逐段命中、未命中即停，都是技能规则；伤害层只该看到“确定要结算的段”。
- on-hit 与 on-damaged 是两种事件。中毒跳伤不是“命中”，不应触发“攻击命中时”的效果；把命中留在技能层，事件边界自然清楚。
- DamageCmd 变成“对已确认的伤害做结算”的步骤，便于单测，不必为了测伤害去构造命中随机数。

### 5.2 为什么固定四阶段

- 暴击是攻方属性，先于守方格挡结算，符合“攻方先亮牌、守方再应对”的直觉；暴击可以被格挡，也符合盾牌格挡重击的直觉。
- 固定顺序让随机数消耗、日志、回放、AI 评估都可复现；顺序一旦可变，组合效果就无法稳定测试。
- “后阶段读取前阶段”覆盖了绝大多数反应式设计：暴击后附加流血、格挡后减伤/回怒/反击、受伤后反伤。只有“回写已完成阶段”做不到，而这个限制很窄（见 6.1）。
- 全事件驱动（3.1 的方案 C1）看似灵活，但把顺序责任推给每个内容作者，最终会产生循环依赖和不可复现的结算；MVP 不采用。

### 5.3 为什么“一条流水线、两套公式、一个施加出口”

- 如果完全分离，扣血、溢出、死亡、受伤事件要写两遍；毒疗、吸血、反伤、伤害数字都要按形式分支。这些是跨形式关注点，应该只实现一次。
- 如果完全统一，百分比伤害就要伪造 `Power` / `Attack` / `Defense`，或者让每个阶段都写 `if (Form == Percent) continue`。前者语义错误，后者把形式分支散落到所有阶段。
- 分层后，差异被收敛到“公式 + 形式适用性表”一处；新增形式（如 `Fixed`）只需加一行公式和适用性，不需要动施加出口。
- 统一阶段名让 Buff 可以写“任意伤害”的 Hook（如“受到伤害时”），不必知道伤害来自技能还是中毒；需要区分时读 `Form` / `Tags` 即可。
- 毒疗是检验该设计的关键案例：它是“取消并替换”，不是“减伤”。如果百分比伤害有独立的施加路径，毒疗就要在两条路径各写一次；统一出口后，它只是 `BeforeApply` 的一个 Hook。

### 5.4 为什么百分比伤害不接受通用 Modifier

- 这类伤害的设计角色是“可靠、无视防御的持续消耗”；如果吃攻防和通用增减伤，它会退化成另一种直接伤害，平衡旋钮也会和直接伤害纠缠。
- 它的平衡旋钮是 `Ratio` 与 `MaxHealth`，来源固定、可预期；这正是 DOT 在战棋中作为“逼迫移动/消耗资源”工具的价值。
- 毒疗证明这类伤害仍需要被干预，但干预点是“是否发生/是否替换”，而不是“乘多少”。把它放在施加阶段，既保留了“不吃 Modifier”的承诺，又允许内容表达例外。
- 代价是：高减伤单位仍会被毒/烧/沙暴稳定消耗。这是有意设计，不是漏洞；如果未来需要“持续伤害加成”，应新增显式的百分比伤害修正，并重新评估本文（见 7.2）。

## 6. 代价与影响

### 6.1 已知限制：同一伤害包内不能回写已完成阶段

| 想要的效果 | 能否表达 | 实现位置 |
| --- | --- | --- |
| 格挡后本次伤害 +50% | 能 | `AfterBlock` 修改第 3 步的独立因子 |
| 格挡后回怒 / 上 Buff | 能 | `AfterBlock` 触发效果，影响后续 |
| 格挡后反击 / 追击 | 能 | `AfterBlock` 入队一个新伤害包 |
| 格挡后本次暴击率 +50% | 不能 | 暴击已在第 1 步完成；改为影响下一次攻击的 Buff，或一个自带暴击判定的追击包 |
| 暴击后附加流血 | 能 | `AfterCrit` / `AfterApply` 施加 Buff |
| 暴击后本次伤害再 +50% | 能 | `AfterCrit` 修改第 3 步的因子（第 3 步尚未执行） |
| 受伤后反伤 | 能 | `AfterApply` 入队新伤害包 |

“格挡不能影响暴击”具体指不能回写同一伤害包内已完成的暴击判定；格挡后增伤、回怒、上 Buff、反击都不受影响。原因是信息单向流动：后阶段可以读前阶段，前阶段不能读后阶段。这个规则同时保证了顺序确定、无循环依赖。

如果未来确实需要在同一伤害包内回写，至少有三条路：把格挡移到暴击之前（改变“暴击可被格挡”的语义）；把暴击与格挡合并为一次联合判定（2×2 结果表，用条件概率表达“格挡后暴击率 +50%”）；或引入重结算（重掷暴击并重算伤害）。三者都会改变现有的判定模型或顺序契约，需要新 ADR。

### 6.2 其他限制

- 百分比伤害不吃通用减伤/增伤：高减伤坦克仍会被 DOT 稳定消耗。这是设计选择，不是遗漏。
- 所有独立增伤/减伤乘算，收益递减，无法叠到 0；完全免疫必须用 `Negated`。
- 形式适用性表是集中知识：新增形式要改表；Hook 作者要知道当前形式会触发哪些阶段。
- 伤害流水线内共 4 个阶段 × 2 个检查点 + `OnDeath`；命名和文档不清时，内容作者容易挂错阶段。
- 同阶段多个 Hook 的触发顺序与冲突解决依赖 ADR-004；数值合并规则见 4.2 规则 5。在 ADR-004 定稿前，组合行为仍是待验证假设。

### 6.3 成本与风险

- 需要实现：Context、阶段调度、Hook 注册/注销、随机数服务、反应队列、伤害日志。MVP 可先只做 `Direct` + `PercentMaxHealth` 两种形式和最小 Hook 集。
- 调试成本上升：组合效果出错时，必须能打印每阶段的输入/输出/随机数；没有伤害日志，这套流程不可维护。建议把结构化伤害日志列为 MVP 的一部分，而不是事后补。
- 测试成本：需要覆盖形式 × 判定 × 修正 × 死亡 × 多段的组合；建议用表驱动测试并固定随机种子。
- 迁移：如果已有技能直接改 Health 的路径，需要收敛到统一施加出口；否则会绕过受伤事件和死亡处理。

### 6.4 关联影响

- **ADR-004（战斗流程中的 Hook，草案）**：需要补充 Hook 派发顺序、优先级、注册生命周期；本文只定义阶段与权限。
- **技能层**：需要新增“确认命中段”的契约，明确单次/逐段命中、段数、目标顺序。
- **Buff**：DOT 的触发时机与层数属于 Buff 生命周期；Buff 需要在 tick 时创建百分比伤害 Context。毒疗用 `BeforeApply` 取消并转为治疗；寄生种子用 `AfterApply` 按 `AppliedAmount` 治疗 `Source`。
- **UI/AI**：伤害预览使用期望值函数，不消耗随机数；伤害数字读取 `AppliedAmount`，溢出单独记录。
- **测试/回放**：固定种子 + 固定消耗顺序；日志记录每段结果。

### 7.2 后续设计范围与重新评估条件

已确定的基线：

- 暴击与格挡采用概率判定，概率合并遵循 4.2 规则 5；改为确定性格挡需要重新评估 `BlockChance` 的语义。
- 暴击倍率与格挡倍率读取对应属性的当前值，属性内的 Buff 合并遵循 ADR-003，独立伤害因子遵循 4.2 规则 5。
- 当前公式不引入额外随机伤害浮动；若引入 0.85–1.0 等浮动，需要重新评估预览、随机数消耗与取整规则。
- 死亡按 4.2 规则 10 立即判定，`OnDeath` 在 `AfterApply` 之后触发；延迟到行动结束属于后续变更。
