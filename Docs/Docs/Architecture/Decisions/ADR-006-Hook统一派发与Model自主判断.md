# ADR-006：Hook 统一派发与 Model 自主判断

> 状态：已确定
>
> 创建日期：2026-10-24
>
> 决策日期：2026-10-24
>
> 本记录描述架构决策；“已确定”不表示接口已定稿或代码已实现。实现与验证进展见第 7 节。

## 1. 背景

项目采用 [ADR-001](ADR-001-选择Hook与Model架构.md) 确定的 Hook & Model 架构，Model 表达内容自身的状态与行为，通过公共 Hook 参与战斗流程。

Model 归属于一个单位，但它关心的事情不一定发生在该单位身上。例如：

- A 的被动在队友 B 受到伤害后触发。
- A 的光环为队友 B 对敌人 C 的攻击增加伤害。
- A 的遗物或被动在任意敌人死亡后触发。
- B 身上的保护效果在施加者 A 死亡后移除。

当前整体原型没有统一这类参与范围：伤害阶段主要收集 Source 与 Target 的 Model，受伤、击杀及 Buff 变化通知主要向特定单位派发，回合结束则遍历全场。现状见 [DamageCmd](../../../Prototype/Combat/DamageCmd.ts)、[BuffCmd](../../../Prototype/Model/Buff/BuffCmd.ts) 与 [CombatManager](../../../Prototype/Combat/CombatManager.ts)。只按归属筛选参与者，会使第三个单位的 Model 无法响应相关事件。

## 2. 面临的问题

MVP 阶段，如何让 Model 保持自身归属，同时响应其他单位相关的公共战斗 Hook？

本次决定公共 Hook 的候选范围、内容条件的归属，以及它与阶段权限、实例生命周期的边界。判断标准是内容行为内聚、支持跨单位效果、机制简单，以及行为可复现和可测试。

本次不确定完整 Hook 清单、通用优先级、阵营和空间查询接口，也不设计伤害转移等具体玩法的结算规则。

## 3. 候选方案

| 方案 | 核心做法 | 优点 | 代价与风险 |
| --- | --- | --- | --- |
| A：按事件参与单位派发 | 伤害主要向 Source / Target 的 Model 派发，其他通知限定持有者 | 延续当前局部派发方式 | 第三方 Model 无法自然参与，业务流程需额外寻找监听者 |
| B：观察统一派发，跨单位干预另行注册 | 通知面向全场，修改当前事件的第三方效果走独立注册机制 | 可以分别管理通知与干预参与者 | 内容需要理解两套参与机制；注册本身不能解决数值合并与冲突 |
| C：公共 Hook 统一派发，Model 自主判断 | 遍历当前战斗作用域内的有效 Model，由各 Model 在具体 Hook 内判断条件 | 同一机制表达自身与跨单位效果，条件和行为留在内容中 | 增加遍历与条件检查；内容遗漏条件可能影响无关事件 |

## 4. 最终决定

MVP 采用方案 C：**公共战斗 Hook 向当前战斗作用域内的所有有效 Model 统一派发，Model 自己在对应 Hook 中判断是否产生效果。**

### 4.1 归属不限定关注对象

Owner 表达 Model 的归属与状态管理关系，不作为公共 Hook 只能涉及该单位的限制。跨单位效果仍属于原来的 Model，不需要为了收到通知而复制或挂载到其他单位。

派发器不再仅因为 Model.Owner 不属于 Source / Target，就排除该 Model。收到 Hook 不等于触发效果。

### 4.2 在具体 Hook 中判断条件

Model 按需覆盖公共 Hook，并利用上下文判断来源、目标、阵营、距离、标签或其他状态。未覆盖的方法使用基类默认行为；通知类默认为空操作，返回修正值的 Hook 应使用各自契约规定的中性值。

同一个 Model 在不同 Hook 中可以关注不同对象。例如，保护效果在伤害修正时关注 Owner，在死亡通知时关注 Applier。因此，MVP 不要求每个 Model 声明一个统一的 Self / Ally / All 范围，也不要求以单个 IsAbout(subject) 方法表达全部条件。

阵营和空间判断可以复用公共查询能力；各 Hook 如何组合这些条件仍由内容决定。相关查询的具体接口留待实现，不在本 ADR 中定稿。

### 4.3 统一派发同时适用于通知与干预

修改当前事件的 Hook 也可以向全场有效 Model 派发。第三方 Model 在满足条件时，可以通过该检查点允许的接口提交修改；MVP 不为跨单位干预单独引入拦截器注册体系。

统一派发不扩大 Hook 的修改权限。阶段能力继续遵循 [ADR-005](ADR-005-伤害结算流程.md)：

- 已定稿的阶段结果不能回写；后续阶段只能使用当前仍开放的能力。
- Before / After 表示相对于某个阶段的位置，不能直接等同于可写 / 只读。
- 当前 AfterCrit、AfterBlock 可以影响后续伤害计算，AfterCalc 仍有施加阶段的修正能力；实际接口与进展见 [伤害结算实现](../../Implementation/Prototype/伤害结算实现.md)。
- 修正合并、取消与替换的冲突由业务结算契约决定，不能仅凭 Model 的遍历顺序推导。未确定的通用优先级仍留待 ADR-004。

例如，A 持有友军增伤 Model，B 攻击 C。A 的 Model 收到伤害计算 Hook，确认 B 是符合条件的友军后提交增伤；A 无须成为本次伤害的 Source 或 Target。

### 4.4 派发器负责集合与调用规则

战斗级上下文提供统一的候选集合，派发器依次完成候选快照、有效性检查与具体公共方法调用。集合最终由 BattleRuntime 还是其他战斗状态对象提供，留待实现确定。

- 每个检查点开始时，对整个派发范围统一拍一次候选快照；不能遍历到某单位时才临时收集它的 Model。
- 顺序必须明确且稳定。MVP 按战斗中的固定单位顺序，每单位按 Buff 加入顺序、技能加入顺序派发；不按每次事件的 Source / Target 重新排序。
- 同一 Model 实例在同一检查点最多调用一次；不同单位持有的同类 Model 是不同实例。
- 调用前再次检查实例是否仍有效。当前检查点中被移除的 Model 跳过，新加入的 Model 从下一检查点参与。
- 派发器不判断“是否是队友”“是否在范围内”等内容条件。

这里的“全场”是当前战斗的有效监听者集合，不包括其他战斗、未加入战斗或已移除的任意 Model。存活状态与具体 Hook 的参与资格需要遵循生命周期契约，不能仅用 HP > 0 过滤所有通知；致死包仍须完成 ADR-005 规定的 AfterApply 与 OnDeath 等收尾。死亡后是否继续监听未来事件，见第 7 节未决事项。

### 4.5 适用边界

本决策只针对公共战斗 Hook，不要求把 OnApply、OnRemove、OnPlay 等专属实例入口向全场广播。它也不改变 ADR-003 中 Buff 通过生命周期回调登记和移除属性 Modifier 的决定。

继续使用有类型的公共虚方法派发，不引入通用字符串事件总线。MVP 暂不引入订阅索引、声明式 Scope 或额外监听注册表；后续若增加候选集合优化，必须保持相同的内容语义。

## 5. 决策理由

### 5.1 内容条件与效果保持内聚

业务流程只需知道当前发生了哪个公共检查点，不需要知道哪些技能或 Buff 会关心它。新增跨单位被动可以在 Model 中表达条件与行为，不必因此修改伤害命令或死亡通知中的参与者选择。

这是对职责边界的设计选择；全场遍历的实际性能与维护成本仍待原型验证。

### 5.2 跨单位不构成另一种 Hook 机制

自身减伤与友军减伤的主要区别是条件，而非是否属于伤害计算。通过 Context 限定阶段能力，通过结算器约束修正合并，可以让两者使用同一套派发机制。单独注册第三方干预并不能代替冲突规则。

## 6. 代价与影响

- **遍历开销**：每个公共检查点需要遍历战斗内有效候选 Model；规模和性能尚未验证，不预设无需优化。
- **条件遗漏风险**：原来依赖局部派发的 Model，在广播后可能影响无关事件。迁移时须逐个审查覆盖的方法，补足条件，不能假设已有行为自然不变。
- **顺序变化风险**：伤害阶段由 Source → Target 改为固定战斗顺序，可能改变依赖先后调用的组合效果；需要验证，不能将迁移全部视为纯重构。
- **受影响模块**：战斗级 Model 集合获取、DamageCmd、BuffCmd、CombatManager 及现有 Model。实现时需同步更新实现记录，明确哪些派发点已迁移。
- **诊断需要**：跨单位效果需要能追踪响应的 Model、Owner、检查点及提交的修正；诊断数据结构留待实现确定。
- **文档关系**：本文确定公共 Hook 的参与范围，补充 ADR-001；ADR-005 继续规定伤害阶段及权限，ADR-004 继续承载完整战斗时机与尚未确定的优先级。

## 7. 后续验证事项

截至本决策创建时，整体原型仍采用第 1 节描述的混合派发方式；本 ADR 尚未完成代码迁移。以下为待验证计划，不代表已有测试通过。

| 验证场景 | 预期结果 / 通过标准 | 进展与证据 |
| --- | --- | --- |
| 队友受伤后触发 | A 的 Model 收到 B 的受伤通知，仅在友军等条件满足时产生效果 | 待验证 |
| 第三方参与伤害修正 | B 攻击 C，A 的友军增伤 Model 生效，A 不属于 Source / Target | 待验证 |
| 任意敌人死亡 | A 的 Model 响应敌方死亡；友方死亡不触发同一效果 | 待验证 |
| 同一 Model 的不同条件 | 伤害修正关注 Owner，死亡通知关注另一关联单位，两者分别正确触发 | 待验证 |
| 现有内容迁移 | 御势、毒疗、击杀再动与技能追踪等不因扩大派发范围错误触发 | 待验证 |
| 自伤与相同内容实例 | 自伤不重复调用同一实例；不同单位的同类 Model 均可独立响应 | 待验证 |
| 检查点中增删 Model | 被移除实例跳过；新增实例从下一检查点参与，包括跨单位增删 | 待验证 |
| 阶段权限 | 第三方可提交当前阶段允许的修改；不能回写已完成阶段或在窗口关闭后调用修改接口 | 待验证 |
| 致死包收尾 | 不因统一的存活过滤而丢失致死包的 AfterApply、受伤与死亡通知 | 待验证 |
| 确定性与规模 | 同种子、同输入、同单位及加入顺序得到一致结果；记录代表性规模下的检查点开销 | 待验证 |
