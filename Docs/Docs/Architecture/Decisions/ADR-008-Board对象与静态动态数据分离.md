# ADR-008：Board 对象与静态动态数据分离

> 状态：已确定
>
> 创建日期：2026-11-03
>
> 决策日期：2026-11-03
>
> 本记录描述 Board 的结构与职责；移动规则、寻路与战斗集成的完成情况分别记录。实现与验证见第 7 节。

## 1. 背景

新 UE 项目已有六边形生成器、`FHexCoord`、`FHexCellData` 和 `UHexGridDataAsset`，需要开始实现运行时棋盘。生成器提供基础地图数据，未来允许策划在编辑工具中调整格子定义，例如将河流标记为不能站立。

当前移动 MVP 将可进入与可停留使用同一套规则，不实现格间高度差限制、墙边阻挡、元素状态或逐格效果。保留已有生成阶段的高度、坡度与站位采样。ZOC 是后续 MVP 功能，本次只记录接入思路。

本决策细化 [ADR-007](ADR-007-移动系统与寻路算法解耦.md) 中 Board 的对象形态、数据组织与位置归属；不要求同时实现其规划缓存等内容。

## 2. 面临的问题

如何组织 Board，使不可变地图定义和本场战斗的占位各自清晰，并为后续移动规则与 ZOC 查询提供基础？

优先考虑生命周期明确、状态一致、保留生成工具成果，以及 MVP 实现规模可控。

## 3. 候选方案

| 方案 | 核心做法 | 优点 | 代价与限制 |
| --- | --- | --- | --- |
| UObject Board | 宿主显式创建和持有一场战斗的棋盘 | 可以独立重建，逻辑查询不要求场景 Actor | 宿主负责初始化和强引用 |
| UWorldSubsystem Board | 自动创建并随 World 管理生命周期 | 提供世界级统一访问入口 | 战斗重开仍需重置，战斗和 World 生命周期未必相同 |
| Actor Board | 关卡内放置带组件的棋盘对象 | 便于场景配置与表现 | 当前数据职责没有场景组件需求 |

数据组织另比较单个混合格子结构与定义/状态分离。选择分离，以区分地图配置与运行时写入，并避免把单位占据写回地图资产。

## 4. 最终决定

### 4.1 对象与生命周期

- 使用具体的 `UBoard : UObject`；暂不建立通用棋盘抽象基类。
- 由宿主通过 `NewObject<UBoard>(Host)` 创建，以 `UPROPERTY` 标记的 `TObjectPtr<UBoard>` 持有。不自动注册为 Subsystem，不放置到关卡。
- 当前不强制建立新的战斗管理类，也不自动接入 GameMode。宿主接入是下一阶段工作。
- 所有访问在游戏线程完成。重开战斗可重新初始化或创建新 Board。
- 格子使用值类型结构体，不为每格创建 UObject。

### 4.2 静态地图定义

`CellDefinitions` 使用 `TMap<FHexCoord, FHexCellData>`，完整保留已定义格子，包括不能站立的格子。

| 字段 | 语义 |
| --- | --- |
| Coordinate | 六边形轴向坐标，与 Map 键一致 |
| WorldLocation | 世界站位点，Z 分量保留高度 |
| bStandable | 基础地图是否允许站立，默认 false，不包含当前单位占据 |

生成器提供初始值，未来策划工具可覆盖；这类编辑工具本次未实现。Board 初始化复制资产，之后只提供查询副本。运行期间修改资产不会改变已初始化的 Board。

现有资产以 `FVector2D(Q, R)` 为键。初始化时验证它与 `Coordinate` 完全一致、世界位置有限，再转换为 `FHexCoord` 键；不静默取整或修复冲突。失败保留旧棋盘，成功替换定义并清空动态状态。空资产是合法空棋盘，空指针不是。

将原字段 `bIsPassable` 改名为 `bStandable`，同步生成器与测试，通过 `[CoreRedirects]` 的属性重定向支持旧序列化字段名。既有高度/坡度/碰撞采样行为保留。墙描述格间关系，未来需要时另行增加边数据，不用某一格的站立标记代替。

### 4.3 动态占位及位置归属

`CellStates` 使用 `TMap<FHexCoord, FBoardCellState>`，当前只有 `OccupantUnitId`。使用战斗内唯一、非负的 `int32` 单位实例 ID，`INDEX_NONE` 表示无人占据；宿主负责分配并在本场战斗中不复用 ID。

动态记录按需创建。已有格子没有记录表示默认空状态；未知格子查询失败。当前仅在有占据者时保存记录。

- `PlaceUnit`：要求格子存在且空闲，单位尚未占据其他格子。
- `MoveUnit`：要求单位已放置、目标存在且空闲；起终点相同返回失败。完成所有检查后，在一次调用中更新起终点。
- `RemoveUnit`：移除该单位的占位；单位不存在返回失败。
- 失败不改变占位。以上接口是占位写入入口。
- 单位位置从占位查询得到，暂不维护独立位置表或反向索引。单位位置查询目前线性扫描动态记录，实际规模需要时再优化。
- 后续 CombatState 如需位置视图，读取 Board 或由统一提交入口维护，不另建可独立修改的权威位置。

两个 Map 都标记为 `Transient`，因为运行时从地图资产重建。“静态”表示本场战斗期间不变，不表示 Board 需要将它持久化。

### 4.4 与规则及执行的边界

Board 邻接查询只返回存在的六边形几何邻居，固定顺序为 `(1,0)`、`(1,-1)`、`(0,-1)`、`(-1,0)`、`(-1,1)`、`(0,1)`。不筛掉不能站立、已占据或高度不同的格子。

Board 的占位提交只检查数据一致性，**不检查 bStandable、格间高度差、路径邻接、行动资格或预算**。上层结合 MoveRule、搜索结果与行动状态，在调用前完成合法性校验；MoveRule 本身负责合法转移和费用，不负责累计预算或行动资格。这是低层提交接口，不应直接绑定玩家移动输入。此边界使以后飞行等规则可以解释相同地图定义，而不必修改 Board。

Board 不扣资源、不执行动画、不派发逐格 Hook。未来接入战斗资源时，由上层统一完成行动校验与提交。本次不引入移动版本号或搜索缓存。

### 4.5 ZOC TODO 与实现思路

ZOC 仍在移动 MVP 计划内，但目前缺少单位注册表、阵营、控制能力和 MoveRule；本次不返回恒定的空 ZOC 结果，不添加不可用的公开查询接口。

接入顺序：

1. 明确单位注册表如何根据 ID 查询阵营与控制能力，以及 MoveRule 如何计算某单位的控制范围。不要预先把 ZOC 固定为一圈相邻格。
2. 增加目标格的控制来源查询。第一版结合 Board 占位及单位信息直接计算，返回全部来源；来源至少能追溯到单位 ID，再由单位信息确定阵营。
3. 允许同阵营多个来源和双方来源同时存在。MoveRule 消费结果，解释 ZOC 对移动的作用；具体作用另行确定。
4. 用单位移动/移除、能力或阵营变化，以及重叠控制的案例验证查询结果。
5. 若实测需要缓存，在 `CellStates` 保存来源集合或可靠计数，并登记上述变化的失效入口。不能用单个阵营字段或 bool 代替来源关系。

以后添加格子效果或 ZOC 缓存时，释放占位只能清除占据字段，必须保留格子的其他状态；当前移除整条动态记录仅适用于状态只有占位的阶段。

## 5. 决策理由

Board 当前承担数据与查询职责，选择 UObject 可以显式匹配战斗生命周期。定义与状态分离，允许复用地图资产，同时为每场战斗独立创建占位。以 Board 占位作为当前位置来源，减少重复状态需要同步的入口。

ZOC 先按需计算是控制一致性成本的设计选择，没有性能优于缓存的实测结论。几何邻接与移动规则分开，延续 ADR-007 的搜索解耦方向。

## 6. 代价与影响

- 宿主需要显式初始化并持有 Board；当前没有自动创建或战斗输入集成。
- 占位接口调用者必须先完成玩法校验，不能把写入成功理解为合法移动。
- 单位位置查询为线性扫描，未来优化时必须保持同一权威数据来源。
- 现有生成器和测试改用 `bStandable`，地图资产存储格式暂保留 `FVector2D` 键。
- 本决策收敛当前 Board MVP；旧移动子系统文档中的复杂停留规则、缓存和迁移计划不表示本次已经实现。
